# 3. Аудит и план разработки

Аудит исходников на 18.09.2026. Файлы: `server/index.mjs`, `server/domain.mjs`, `public/app.js`, `render.yaml`, текущие тесты. Это обзор готовности, не независимый пентест. Перечисленные ниже изменения пока не внесены.

## Что уже можно сохранить

- Визуальную концепцию и мобильное меню.
- Серверный пересчёт цены, проверку количества и добавок.
- Проверку подписи Telegram и принадлежности заказа сессии.
- Разделение тестового и боевого режима провайдера.
- Сверку суммы, валюты, заказа и статуса перед отметкой оплаты.
- Базовый процесс одноразовой выдачи в одном процессе сервера.
- Локальные автотесты и браузерный сценарий.

SQLite подходит для многих небольших систем. Причина менять модель здесь — требования к нескольким процессам, восстановлению, данным разных клиентов и эксплуатации, а не утверждение «SQLite всегда плоха». Сложный фронтенд-фреймворк также не является обязательным условием надёжности.

## Недостатки, которые нельзя скрывать при продаже

Приоритет **P0** — решить до реальных денег/покупателей. **P1** — решить до коммерческой круглосуточной эксплуатации. **P2** — развитие после пилота. У каждого пункта есть наблюдаемый критерий.

| Приоритет | Что найдено | Последствие | Что должно стать результатом |
|---|---|---|---|
| P0 | `allOrders()` выбирает только последние 500 записей; webhook ищет платёж внутри этого списка | Старый оплачиваемый заказ может не найтись, событие получит успешный ответ; история покупателя зависит от чужих заказов | Поиск по индексированному ID платежа во всей БД, история с фильтрацией по владельцу до пагинации; тест заказа старше 500 новых |
| P0 | `paymentLocks` — Map в памяти; нет долговременного журнала задач | Перезапуск теряет координацию; несколько экземпляров не разделяют блокировку | Платёжные попытки в БД, уникальные ограничения, обработчик повторов и восстановление после падения |
| P0 | `paymentFor()` получает ответ ЮKassa и только затем сохраняет paymentId; неизвестный webhook получает 200 | Возможна потеря своевременного уведомления при совпадении событий/сбое | Сохранять входящие события, разрешать связи по проверенным данным, выполнять независимую сверку |
| P0 | Нет фоновой сверки; обновление зависит от webhook и кнопки клиента | Деньги могут быть подтверждены у провайдера и долго не попадать на кухню | Worker восстанавливает неизвестные/ожидающие платежи без участия покупателя; уведомляет о расхождениях |
| P0 | `capture:true`, универсальный `full_payment`, нет модели чеков | Нельзя считать фискализацию корректной для любого заведения | Утверждённый кассовый сценарий и проверенные чек оплаты/зачёта/возврата для него |
| P0 | Нет возвратов и их синхронизации | Отмена в кабинете провайдера не отражается автоматически в приложении | Частичный/полный возврат с полномочиями, статусом, причиной, ключом повторов, чеком и сверкой |
| P0 | `render.yaml` размещает основную SQLite-базу на Render | География платформы не даёт российской базы по этой конфигурации | Утверждённая схема данных и выбранная инфраструктура; прежний Render оставить демонстрацией |
| P0 | Нет графика, срока жизни заказа, резервов и перепроверки доступности перед оплатой | Старый заказ можно оплатить после изменения меню/закрытия | Ограниченный по времени checkout, график и паузы, политика поздней оплаты и возврата |
| P1 | Один пароль администратора и одна роль | Нельзя установить виновника или уволить одного кассира без затрагивания всех | Именные сотрудники, роли, MFA для владельца, отзыв сессий, аудит действий |
| P1 | Ключ rate limit берётся из `req.socket.remoteAddress`, состояние лимитов в памяти | За reverse proxy пользователи могут делить лимит; разные процессы имеют разные счётчики | Доверенная конфигурация прокси, лимиты по назначению и субъекту; тест через настоящий ingress |
| P1 | Вся запись заказа — JSON, обновление без версии строки | При усложнении и нескольких процессах возможны потери изменений | Типизированная схема, миграции, транзакции и разрешённые переходы через условные обновления |
| P1 | `/api/health` всегда возвращает `ok` | Внешняя проверка не замечает поломку БД и фоновых задач | Раздельные liveness/readiness и сквозной безопасный мониторинг |
| P1 | Нет процедуры backup/restore, RPO/RTO не измерены | После потери диска неизвестно, что и как восстановить | Проверенные копии, восстановление на новом окружении, финансовая сверка после восстановления |
| P1 | Журналирование только через `console.error`, нет уведомлений и аудита | Об ошибке первым сообщает покупатель | Структурированные журналы без секретов, метрики, дежурный и инструкция действий |
| P1 | Заказы появляются в админке через опрос; нет отдельного подтверждения «кухня увидела» | Заказ может остаться без внимания при спящем планшете | Явное принятие, повторный сигнал, контроль связи с кухней, автопауза по согласованной политике |
| P1 | Товары и реквизиты зашиты в коде | Каждому клиенту нужна ручная переделка и нет удобного управления | Настройки бренда/точки, редактор меню, варианты, добавки, история цен и стоп-лист |
| P1 | Нет сроков хранения, выгрузки и процедур работы с данными | Не определено, как исполнить запрос владельца или покупателя | Карта данных, права, сроки, экспорт/удаление с исключениями для обязательного хранения |
| P1 | Нет воспроизводимого развёртывания и передачи клиента | Новый подрядчик зависит от твоих знаний и аккаунта | Сборка, конфигурация, миграции и восстановление по инструкции в клиентском аккаунте |
| P2 | Нет нескольких точек, доставки, лояльности и POS-интеграции | Прототип не покрывает сеть или сложный общепит | Отдельные требования и интеграции после проверки ядра |

Для single-process прототипа нельзя автоматически утверждать наличие всех гонок из многопроцессной версии. Однако изменение масштаба требует новых гарантий; текущие Map и синхронный SQLite-код сами по себе их не дают.

## Разработка по этапам

### Этап 0 — спецификация пилота

Зафиксировать продавца, одну точку, часы кухни, самовывоз, путь оплаты, кассовый сценарий, роли, владельцев аккаунтов, поддержку и бюджет. Встреча с владельцем + бухгалтером + специалистом POS/кассы, если есть.

**Готово, когда:** сценарий от заказа до возврата нарисован и согласован; ясно, на чей счёт поступают деньги, кто формирует каждый чек и кто отвечает ночью. Пока нет этих ответов, нельзя честно назвать точную стоимость интеграции.

### Этап 1 — структура и данные

Разделить монолитный файл на модули: конфигурация, каталог, авторизация, заказы, оплата, чеки, администрирование, задачи. Нормально форматировать код. Добавить строгую валидацию входных данных; TypeScript полезен для сопровождения, но не подменяет проверку данных во время выполнения.

Подключить PostgreSQL, создать версионируемые миграции, суммы в копейках и явные связи. В отдельной установке клиента — отдельная база и секреты. Предусмотреть идентификатор точки без преждевременной общей multi-tenant системы.

**Готово, когда:** чистая база создаётся из миграций, обновляется с предыдущей версии; тесты подтверждают снимки цен, ограничения и разграничение данных.

### Этап 2 — деньги и фискализация

Исправить P0 из аудита. Ввести сохранённые попытки платежей, входящие события, фоновые задания, сверку, раздельные статусы. Реализовать отмены/возвраты, сохранение связи с чеками, обработку неопределённых результатов и запоздалой оплаты.

**Готово, когда:** тестовый магазин проходит успешную оплату, отмену, таймаут, повтор уведомления, перезапуск между запросом и ответом, частичный возврат, ошибку чека, оплату старого заказа. Затем — согласованная малая реальная операция с подтверждением фактического чека и возврата. Боевой тест выполняется только с разрешения продавца.

### Этап 3 — работа заведения

Именные роли: владелец, управляющий, кассир/кухня, при необходимости бухгалтер и техподдержка. Разделить права на изменение меню, возвраты, выгрузку и доступ к секретам. Добавить график, исключения по датам, паузы, время ожидания, подтверждение принятия, звуковой сигнал и заметный статус связи.

**Готово, когда:** кассир выполняет смену без помощи разработчика, уволенный сотрудник теряет доступ сразу, две одновременные выдачи не проходят, нарушение связи не выглядит как пустая очередь.

### Этап 4 — эксплуатация и защита

Раздельные development/staging/production. Сборка закреплённой версии, CI-проверки, миграции, секреты, журнал действий, мониторинг, резервирование, восстановление, план отката. Проверка веб-доступа, Telegram iOS/Android/Desktop, клавиатуры, доступности и нестабильной сети.

**Готово, когда:** другой специалист поднимает систему из переданных материалов; выключение экземпляра приложения, недоступность БД/провайдера и сбой релиза дают ожидаемый результат. Нагрузочный тест задаётся реальным числом заказов/пользователей пилота, а не случайным «выдерживает миллион».

### Этап 5 — ограниченный пилот

Одна точка и ограниченная аудитория. В начале ответственный рядом с заведением; реальные заказы сверяются ежедневно. Ограничить сложность меню, число заказов на слот и способ получения. Есть план остановки онлайн-приёма и возвратов.

**Готово, когда:** заранее согласованный период и объём пилота пройдены без неразобранных финансовых расхождений, сотрудники обучены, проблемы устранены, владелец подписал приёмку. «Неделю не было ошибок» без заказов не является проверкой.

### Этап 6 — повторяемые установки

Добавить шаблон конфигурации клиента, версионирование, матрицу совместимости POS/касс, регулярные обновления и процедуру миграции. Не копировать случайные изменения между папками разных заведений.

**Готово, когда:** второй клиент разворачивается из того же релиза без правок ядра, а обслуживание не зависит от памяти одного человека.

## Проверки, которые должны блокировать выпуск

- Нет доступа покупателя/кассира/другого клиента к чужим данным.
- Повтор checkout/webhook/возврата не удваивает действие.
- Заказ старше 500 новых корректно находится и обрабатывается.
- Подмена суммы, валюты, точки, продавца, подписей и режима оплаты отклоняется.
- Неопределённый ответ провайдера разрешается без повторного слепого списания.
- Возвраты не превышают подтверждённую сумму с учётом предыдущих возвратов.
- Обновление меню не изменяет уже оплаченный заказ.
- Две одновременные выдачи дают одну выдачу и один отказ.
- Сбой между подтверждением оплаты и отправкой задачи кухне не теряет заказ.
- Резервная копия восстанавливается; после восстановления выполняется сверка с ЮKassa.
- Сотрудник без нужной роли не может вернуть деньги или выгрузить покупателей.
- Тестовые уведомления не переводят боевой заказ в оплаченный.
- Telegram, экран оплаты, редирект и cookies работают на целевых устройствах.
- В журналах, репозитории и клиентском JavaScript нет ключей, session cookies, кодов выдачи и лишних персональных данных.

## Чего пока не стоит добавлять

До первого стабильного пилота не нужны маркетплейс, своя платёжная агрегация, Kubernetes, десятки микросервисов, программа лояльности и приложения в двух магазинах. Это не запрет на развитие: эти функции добавляют отдельные денежные и эксплуатационные сценарии, которые нужно уметь поддерживать.
