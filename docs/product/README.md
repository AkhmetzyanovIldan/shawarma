# От прототипа КРУТИ к продукту для заведений

Дата аудита: **18 сентября 2026**. Для Ильдана: ты уже можешь менять код и запускать проект; этот комплект объясняет следующий уровень — деньги, ответственность, надёжность и внедрение.

**Текущее состояние: работающий локальный прототип, не готовый сервис для промышленной эксплуатации.** Наличие красивого интерфейса, тестов и адаптера оплаты не означает готовность принимать реальные заказы круглосуточно. Ниже — проектные решения и критерии готовности, а не утверждение, что они уже реализованы.

## Предлагаемая первая версия

Первая продажа: одна точка, один продавец-ИП или ООО, самовывоз, оплата в его магазине ЮKassa, отдельная установленная копия приложения в аккаунте клиента. Это **предложение для пилота**, а не уже согласованный объём будущего бизнеса. Сеть, несколько продавцов, доставка и самозанятые — отдельные расширения после проверки основы.

Общий код продукта остаётся один. Название, меню, цены, график, адрес, логотип и настройки конкретного клиента — данные. Не создаём несовместимую копию исходников для каждого покупателя.

Твоя услуга состоит из трёх частей:

- право использовать согласованную версию приложения;
- внедрение: настройка, интеграции, обучение, приёмка;
- сопровождение: обновления, диагностика, резервные копии, оговорённая поддержка.

Оплата еды поступает заведению. Оплату своей работы ты получаешь отдельно. Для начала не строим платёжного посредника, который собирает выручку всех клиентов на один счёт.

## Три решения, которые нельзя оставлять «на потом»

**Хостинг.** Ранее подготовленный Render подходит для демонстрации на синтетических данных, но не является автоматически подходящим местом для базы покупателей из РФ. У Render нет российского региона; правовой режим хранения и передачи данных надо учесть до запуска. См. [географию Render](https://render.com/docs/regions) и [письмо Минцифры о новых правилах локализации](https://www.consultant.ru/document/cons_doc_LAW_511584/). Для проектирования предлагаю основную обработку заказов, базу, логи с персональными данными и резервные копии в РФ. Это архитектурное решение; юридическую схему подтверждает специалист по 152-ФЗ.

**Фискализация.** Оплата, чек и выдача — разные события. Текущий код с одним `full_payment` не покрывает автоматически любой сценарий общепита. Схему утверждают бухгалтер заведения и поставщик кассового решения. [ФНС о предоплате](https://www.nalog.gov.ru/rn92/news/activities_fts/16621080/), [ФНС о разных сценариях общепита и доставки](https://www.nalog.gov.ru/rn93/news/activities_fts/16618680/).

**Независимость клиента.** Она появляется благодаря владению инфраструктурой, правам на установленную версию, передаче исходников/сборки и проверенной процедуре передачи другому специалисту. Одного обещания «я не отключу» недостаточно.

## Что выполнено на этом этапе

- Изучены текущие сервер, каталог, тесты, документация и конфигурация Render.
- Повторно выполнены пять существующих автотестов — прошли. Они проверяют прототип, а не все требования коммерческого продукта.
- Подготовлен этот комплект: решения, аудит, требования, план развития, порядок внедрения, действия при авариях, ответы на вопросы и учебные задания.
- Промышленная архитектура, реальные возвраты, новая база, роли, мониторинг и подключения клиентов **ещё не реализованы**.

Не нужно сразу учить всё администрирование или писать все функции. Нужно уметь объяснять каждый денежный переход, отличать подтверждённое событие от предположения и воспроизводимо восстанавливать систему. Двигайся по этапам с измеримыми результатами.
