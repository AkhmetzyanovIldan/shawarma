# GPT-6 Astra: подход для этого проекта

Исследование: 15 сентября 2026 года. Название модели в официальной документации — **GPT-6 Astra** (`gpt-6-astra`). Универсального доказанного «самого лучшего» набора навыков или настроек нет: полезность определяется задачей.

## Что взято из официальных рекомендаций

В [руководстве GPT-6 Astra](https://developers.openai.com/api/docs/guides/latest-model) OpenAI рекомендует явно задавать автономность, границы задачи, стиль ответа и глубину проверки. Инструкции навыков и AGENTS.md нужно проверять на конфликты. Для небольших правок не нужны бесконечные повторные тесты.

В [рекомендациях по фронтенду](https://developers.openai.com/api/docs/guides/frontend-prompt) полезны явное визуальное направление, продуманная типографика, реальные изображения, иерархия и адаптация под мобильный экран. Здесь это преобразовано в конкретную концепцию: кремовая бумага, цвет гриля, плотный заголовок, фуд-фото, минимум шагов от меню до заказа.

## Какие навыки использованы

- **OpenAI Docs** — поиск и проверка официальных рекомендаций по указанной модели.
- **Sites building** — последовательность работы над интерфейсом, визуальная концепция, ранний локальный просмотр. Облачная публикация Sites не использовалась: пользователь выбрал локальный запуск и подготовку Render.
- **ImageGen** — авторские фото для первого экрана и карточек. Все финальные изображения хранятся в проекте.

Figma имеет смысл при отдельной задаче на дизайн-файл или существующем макете; для этого проекта промежуточный Figma-файл не нужен. Установка большого пакета сторонних навыков сама по себе не делает интерфейс лучше. Новые сторонние навыки не устанавливались.

## Настройки: практическая рекомендация, не результат бенчмарка

- Для комплексной архитектуры платежей разумно использовать `high`; для небольших правок — `medium` или `low`. Выбор нужно оценивать по качеству и времени конкретной задачи. Максимальный effort не гарантирует лучший дизайн.
- В API Astra не поддерживает `temperature` и `top_p`; для вызова инструментов нужна Responses API. Параметры API не следует переносить буквально в настройки приложения Codex. Источник: [руководство модели](https://developers.openai.com/api/docs/guides/latest-model).
- В этом сеансе глобальные настройки пользователя и выбранная модель не менялись.
- Самые важные критерии качества здесь: мобильная версия, продуманные состояния, визуальная проверка, серверный расчёт суммы и корректная выдача.

## Готовый промпт для следующих итераций

```text
Продолжи проект КРУТИ — Telegram Mini App шаурмечной в Петербурге.
Сначала изучи README и код. Сохрани стиль: кремовый фон, оранжевый акцент,
плотная типографика, настоящие фуд-фото, ясные мобильные экраны.

Нужный результат: [конкретное изменение и ожидаемое поведение].
Пользователь должен суметь: [проверяемый сценарий].
Ограничения: локальная работа, сервер совместим с Render; не публикуй,
не включай реальные списания и не раскрывай ключи без отдельной задачи.

Самостоятельно принимай обычные обратимые решения. Задавай вопросы только
когда ответ существенно меняет результат. Доведи изменение до работающего
состояния, проверь затронутый сценарий и мобильную вёрстку.
Цены, авторизация, подтверждение оплаты и выдача проверяются на сервере.
Сохраняй доступность клавиатуры и состояния загрузки, пустоты и ошибок.
Ответь кратко: что изменилось, что проверено и какие ограничения остались.
```

## Что проверено

Автотесты: подмена клиентской цены, добавки/размер/количество, стоп-лист, подпись и возраст Telegram initData, соответствие платежа заказу, изоляция покупателей, вход/выход администратора, код выдачи, запрет повторной выдачи, сохранение после перезапуска. Браузерная проверка: корзина → демо-оплата → код → кухня → выдача; desktop и mobile.

Боевой платёж и реальный Telegram-клиент требуют тестового магазина, бота и HTTPS-размещения; эти проверки ещё предстоят.
